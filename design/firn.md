Decision: Firn's first public deployment milestone demonstrates Whitefoot through complete standalone Redis application workloads, with an existing application's business logic unchanged and its ordinary client supported, because benchmark commands alone do not establish practical usefulness or distinguish a language advantage from omitted work, instead of releasing a benchmark-only subset or requiring the entire Redis deployment and extension ecosystem first. Cache/session storage and scripted conditional updates are the core workloads; the remaining application selection and command coverage are established against real consumers. Replication, Sentinel, Cluster and unused feature families are later scope, reopened if a selected workload needs them ([deployment direction](../research/investigations/firn/DESIGN.md#deployment-direction)).

Decision: Firn's scripting milestone implements the Redis Lua execution environment in Whitefoot and first tests a vertical slice against Redis's interpreter and representative scripts, because dynamic values, closures, object reclamation and atomic command composition exercise language capabilities that a native engine would not demonstrate, instead of a script-template recognizer, an embedded native Lua engine as the language evidence, or a JIT prerequisite for the first release. VM layout, collection and execution mechanisms remain research questions; inability to meet a real workload's requirements reopens Whitefoot's capabilities rather than excluding the workload to hide the gap ([deployment direction](../research/investigations/firn/DESIGN.md#deployment-direction)).

Decision: The reference release's own Redis suite, Redis 7.2.16's, gates firn as a ratchet of named passing tests, without tolerating errors from the framework's commands, because a lost pass must fail the gate even if another test starts passing, instead of gating on an aggregate count or demanding the entire suite pass before it can protect existing compatibility. Repeated CI runs establish the passing set; tests that pass in only some runs are excluded with their observed frequency recorded, and new passes are reported for addition in the same PR. A test the suite's own timeout has seen making no progress is listed with that evidence and skipped from the start by the gate, because each such test otherwise costs the timeout and a rerun of its unit on every run, which pushed the gate past its time limit once transactions reached more of `unit/multi`, instead of raising the gate's time limit or shortening the timeout every test gets. The suite's external mode and its compatibility limits remain those of the [measurement method](../research/experiments/redis-compat/README.md#method).

Decision: Every extracted reference suite copy explicitly drains and checks the known acknowledgment names and counts at its five argument-free pub/sub removal call sites, for Firn, Redis and external targets alike, because Redis 7.2.16's helper reads zero replies when its name list is empty and otherwise permits another connection's publication to precede removal, instead of changing the wire command or expected recipient count, excluding the tests, delaying publication or making a general helper wait for a combined subscription count to become zero. A contextual zero-fuzz forward-only patch fails on stale input, its application checks run in CI, and run metadata discloses the adjustment; retire it when the pinned suite supplies the barriers ([missing suite barriers](../research/investigations/firn/connection-waits.md#membership-confirmations-and-the-redis-suite-barrier)).

Decision: The recording runs that establish the passing set skip the listed tests as the gate does, and one further run of only the units holding listed tests goes without the list and reports each listed test's outcomes, naming as a candidate to leave the list only a test that passes and keeping listed one that times out, fails or errors, because a listed test run without the list can fail instead of hanging and leave its connection's state behind for the tests after it, as a listed `unit/multi` test of Redis 7.2.16 leaves its connection inside MULTI when its CONFIG SET is refused, so recordings without the list lose passes the gate keeps and an error or failure there does not show that a test stopped hanging, instead of recording every run without the list, dropping the report, or reading an error or failure as a test that stopped hanging.

Decision: The reference server is Redis 7.2.16 built from its release archive and checked against the SHA-256 that `tests/redis-suite/reference.sh` pins, for every reference use (the gate, the consumers, the benchmarks, the recorder and the sync-failure oracle), because Ubuntu 24.04 packages Redis 7.0.15 and an unpinned package or image can move under a run, instead of the distribution's package, Redis's apt repository or its container image.
