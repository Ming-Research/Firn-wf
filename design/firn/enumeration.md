Decision: SCAN, KEYS and RANDOMKEY enumerate the keyspace map through Whitefoot's `map_scan`, whose position cursor returns each key present throughout a scan exactly once while other clients write, SCAN taking one `map_scan` step per request from the client's cursor and KEYS every step in one statement, because that meets Redis 7.0.15's SCAN guarantee, every key present for the whole iteration returned, with no work added to the commands that write keys, instead of an index of keys kept beside the map, which every write would have to update.

Decision: RANDOMKEY picks uniformly among the keys one `map_scan` step of count 15 gathers from a random position, continued from the table's start when it reaches the end short of fifteen keys, drawing a fresh position whenever no key is gathered, and starts over after removing a picked key found expired, because Redis 7.0.15's dbRandomKey draws the same way, a uniform pick among up to fifteen keys gathered from a random bucket onward, wrapping at the table's end (dictGetFairRandomKey) and fresh random buckets when that finds none (dictGetRandomKey), and the pinned runtime's step reads to the table's end when the map holds no more live entries than its count, so with the wrap a keyspace of up to fifteen keys is drawn uniformly, instead of the first live key at or after a random position.

Decision: SCAN removes and records a matched key found expired before deciding whether its type belongs in the reply, excluding the removed key under every TYPE argument, including none, because Redis 7.2.16's [scanGenericCommand](https://github.com/redis/redis/blob/7.2.16/src/db.c#L1134-L1142) rejects a null lookup result, instead of returning the removed key's name under TYPE none.

Decision: All users of the shared glob matcher, currently KEYS, SCAN MATCH, CONFIG GET and the pattern delivery and channel listing of publish/subscribe, obey Redis 7.2.16's maximum nesting of 1000 while keeping the matcher iterative, counting only entry into a nonterminal star suffix after adjacent stars collapse and excluding retries, trailing stars, escaped stars and character classes from the count, because [stringmatchlen_impl](https://github.com/redis/redis/blob/7.2.16/src/util.c#L56-L190) returns no match above that depth even when an unlimited matcher would accept the name, instead of accepting unlimited nesting or limiting the pattern's total star count. A 1001st suffix entry returns no match; a trailing star can still succeed at depth 1000.

Decision: SSCAN, HSCAN and ZSCAN return Firn's existing element order and, while bounded resumable scanning of the ordinary standard-library hash map is missing under board item coord-wfbl-02-01, return the whole MATCH-filtered collection in one held statement with cursor zero; cursor values and batch boundaries are not Redis's, because every continuously present element is included in this terminating scan and COUNT is a hint, while Firn retains no Redis encoding history or listpack order, instead of adding that history and order solely to reproduce Redis's compact-encoding boundaries. Set and hash traversal use the map's visitor, and sorted sets use their existing score/member order; arbitrary valid input cursors and positive COUNT values do not bound this provisional path's work or reply size, and the gap reopens the implementation when the library supplies bounded scanning ([scope and reference](../../research/investigations/firn/collection-scan.md)).

Decision: ZSCAN selects Redis 7.2.16's d2string text when the entire current sorted set has at most 128 members and every member is at most 64 bytes, Redis's default listpack limits, and otherwise selects the retained %.17g writer through score_bytes_17g, always framing scores as bulk strings in both protocols, because the recorded listpack and dictionary scans differ for 0.1, 1e17 and 2/3 while %.17g of a double supplies the dictionary's %.17Lg digits, instead of using one formatter for every size or retaining Redis encoding history. The selection precedes MATCH and ignores stored encoding CONFIG values; removing the last oversized member or shrinking back to 128 members returns to d2string text even though Redis keeps skiplist text after promotion ([recording and divergence](../../research/investigations/firn/collection-scan.md#zscan-score-formats-and-recorded-replies)).

Rejected:
- An index of keys kept beside the keyspace map: rejected because every write would update it, where the map's own cursor enumerates the keys.
- The first live key at or after a random position: rejected because a key's chance then grows with the empty run before it, where Redis averages it over fifteen keys.
- Redis encoding history and listpack order for collection scans: rejected because the selected compatibility scope permits Firn's element order and batch boundaries, and a complete held traversal already meets the scan coverage requirement.
- Reading ordinary-map buckets or resuming a whole-map visitor at a numeric offset: rejected because rebuilds may relocate continuously present entries and skip them between calls; bounded continuation belongs to the standard library under coord-wfbl-02-01.
- Silently dropping entries above a compact-size threshold or reporting cursor zero for a partial result: rejected because a full iteration would then omit entries present throughout it.
- One ZSCAN score formatter for all collection sizes: rejected because Redis 7.2.16's recorded compact text is 0.1, 100000000000000000 and 0.6666666666666666 where its dictionary text is 0.10000000000000001, 1e+17 and 0.66666666666666663.
- Retaining sorted-set encoding history to choose ZSCAN score text: rejected because the selected rule depends on the current complete collection and retains no Redis encoding state; after growth and shrink Redis continues writing skiplist text while Firn returns to d2string, an explicit compatibility divergence rather than a claim of identical promotion history.
- Choosing ZSCAN score text from only the MATCH result: rejected because Redis's encoding and score text belong to the complete sorted set, so an unmatched oversized member must still select dictionary text for the returned members.
