Decision: A script's commands read the clock as it was when the script began, for expiry checks, relative deadlines and TTL replies alike, because every command of one script must judge expiry and relative deadlines against one instant, as Redis 7.2 freezes one time for a whole execution unit ([`commandTimeSnapshot`](https://github.com/redis/redis/blob/7.2.0/src/server.c#L212), set once per [execution unit](https://github.com/redis/redis/blob/7.2.0/src/server.c#L1141)), instead of Redis 7.0.15's freezing of expiry checks alone, under which a TTL reply or a relative EXPIRE inside a long script reads the moving clock.

Decision: A key a script's command finds expired is removed at once and its `DEL` appended to the script's effects, as Redis 7.0.15 removes a key a script's lookup finds expired, because the effects must replay to the state the script left.

Decision: The records a script appends are wrapped in `MULTI` and `EXEC` by the script's caller when it appended more than one, as Redis 7.0.15 propagates a script's effects, because the append-only file must apply a script whole or not at all, instead of each command part wrapping its own records.

Decision: A script initially holds the immutable set of entries named by its original declared KEYS together with Meta for the entire attempt, and an admitted command requiring an undeclared key or the whole map abandons the attempt before that command touches any entry and retries the invocation with the whole keyspace held, because declared entries preserve isolation while standalone Redis 7.0.15 allows computed and undeclared key access, instead of forbidding those commands, expanding the hold during execution or exposing fallback as a Lua error. Whole mode remains selected through later budget retries; modifying the Lua KEYS table does not change the declaration ([attempt protocol](../../research/investigations/script-engines/README.md#proposed-option-a-structures-and-attempt-protocol)).

Decision: A declared-entry attempt saves an owned logical Option<Entry> copy once before a command can first mutate that entry, including lazy expiry, and restores members, values, scores, list order, absolute expiry, access and last-write stamps exactly while allowing collection backing to be rebuilt, because firn has no collection cursor or promised layout-dependent result and ordinary hash-map rehash already changes backing, instead of retrying written effects twice, copying every declared entry at attempt start or requiring an exact layout snapshot. Payloads are restored before first-refresh access stamps; expiry insertions, effects and sequence/capture scratch remain private until acceptance, and a Lua error keeps preceding writes. Reopen if SSCAN, HSCAN, ZSCAN or a layout-dependent result guarantee is added ([rollback](../../research/investigations/script-engines/README.md#rollback-must-include-earlier-writes), [logical restore grounds](../../research/investigations/script-engines/README.md#logical-collection-restore)).

Decision: Script attempts keep Meta held throughout interpreter execution in this correctness step, and budget exhaustion restarts only an attempt without dataset effects while an attempt with effects continues to completion or undeclared-key fallback, because the existing atomic command and metadata interfaces preserve Redis isolation under that hold, instead of claiming disjoint-script concurrency or releasing metadata between commands before a publication contract exists. The shared hold still serializes attempts ([metadata lifetime](../../research/investigations/script-engines/README.md#metadata-sequence-numbers-capture-expiry-and-eviction)).

Decision: Scripts run on a pool of as many Lua engines as the runtime's driver count, which firn reads from the drivers field of its invocation's inputs, at least one and fixed for the run, and a script checks out any idle engine, the one returned last, an engine being made only when none is idle, while one server-wide SHA1/source registry stays the only source and each engine compiles a script from it the first time that engine runs it, because a single engine made every script wait for the one before it, 89% of 50 connections' time in the checkout probe ([engine waits](../../research/investigations/deployment-performance/README.md#where-scripts-wait)), and no more scripts than the driver count can execute at once, instead of driver affinity, which Whitefoot cannot express because it does not expose which driver a context runs on, an option choosing another count, or engines that each keep their own Lua state ([pool ruling](../../research/investigations/script-engines/README.md#question-and-ruling)). Redis 7.0.15 has one Lua state, so the state one script can leave for later ones, math.random's generator and the cjson module's settings, is kept in one canonical copy that each attempt holds together with its keys and Meta, copies into its engine when its statement begins and copies back only when the script ends with its result or a Lua error, an abandoned attempt copying nothing; that copy is an object apart from the pool, because SCRIPT KILL and the taking of engines must reach the pool while an attempt runs. SCRIPT FLUSH clears sources, advances the generation and returns the cjson settings to their defaults while math.random's generator continues, as Redis 7.0.15 starts a new Lua state beside its process-wide generator (Firn-wf probe run 38223467544); an engine made before the FLUSH is replaced when next taken. The shared Meta hold still serializes attempts, so the pool removes the wait for the one engine and not the wait for Meta.

Decision: EVALSHA checks that the registry holds the script's SHA1 before it takes an engine, answering NOSCRIPT there as Redis 7.0.15 does, and, for each attempt whose engine has not compiled that SHA1, reads the registry again and copies the script's source from that read, while an attempt whose engine has compiled it copies nothing, because an engine whose generation is current compiled only scripts registered in that generation, EVAL and SCRIPT LOAD registering a script before they return their engine and EVALSHA compiling only a source it has just read from the registry under the current generation, and only SCRIPT FLUSH, which advances the generation, removes a registered script, so a cache hit never runs a script the registry did not hold when that engine was taken, while copying the source on every call took 2.8 to 3.8% of firn's CPU under rate-limiter-flexible's script ([profile](../../research/investigations/deployment-performance/README.md#result)), instead of copying the source at the check on every call; SCRIPT FLUSH waits until no script is in progress, as Redis 7.0.15 does below its busy threshold, instead of interrupting a running script's later attempts; only an EVALSHA whose FLUSH came after its registry check and before it first took an engine can answer NOSCRIPT because of that FLUSH, as if the FLUSH came first; its first take counts it in progress and records the kills count atomically with reading the generation and taking an engine, so once a script has first taken an engine, FLUSH waits for it until it ends, including between attempts.

Decision: A script compiled by EVAL or SCRIPT LOAD is kept until SCRIPT FLUSH, with no limit on their number and no eviction, and FLUSH frees their sources at once whether SYNC or ASYNC is given, because Redis 7.0.15 keeps every compiled script until its scripting is reset and its FLUSH answers the same either way, instead of the eviction of later Redis versions or a release in the background.

Decision: A command a script calls writes its reply into the client's reply buffer as on the network, and the script receives it converted from those bytes by Redis 7.0.15's redisProtocolToLuaType, while a script's result is written by luaReplyToRedisReply's rules in the client's protocol, because a script's command then runs the network path's own reply writers, instead of a second, Lua-specific result for every command.

Decision: SCRIPT KILL stops a script that has written nothing when its current attempt runs out of budget, the script waiting a millisecond there, then taking an engine again and checking for a kill requested since it first took one, since a context that never waits keeps the others its thread serves from running, SCRIPT KILL's among them, and answers OK while any script is in progress and NOTBUSY while none is, one request reaching every script then in progress that has written nothing, each comparing the pool's one count of kill requests with the count it recorded at its first take, because an attempt holds the keyspace's statement and the pool that records the request is reachable only between attempts, as the selected direction checks for a kill between statements, instead of checking within an attempt, which would nest the pool's statement inside the keyspace's; a script that has written runs to its end, and SCRIPT KILL sent while it does answers OK where Redis answers UNKILLABLE, since the pool does not learn that the script wrote. Correction of OK for a written script waits for Whitefoot request firn-req-attempt-publish under the busy-script backlog; this step keeps that behavior unchanged.

Decision: The commands a script calls reach the scripting module as an interface, ScriptCommands, that the commands module binds to script_command, because the commands module already depends on the scripting module for EVAL's dispatch and a call back into it would close a cycle of modules, instead of moving the script's statement out of the scripting module into the commands module, which would split the Lua environment's handling between the two.

Decision: legacy scripts capture their pre-command OOM state and keep an attempt-local WRITE_DIRTY flag separate from the effects flag, because Redis 7.0.15 scriptVerifyOOM refuses DENYOOM only before an accepted WRITE command, including DEL of a missing key, while firn's effects flag must still control retry and rollback, instead of treating no-effect writes as unwritten for OOM or rechecking memory inside a script; each retry restarts WRITE_DIRTY under the original captured OOM state.

Decision: EVAL and SCRIPT LOAD explicitly refuse every source starting with a shebang, including plain #!lua and allow-oom or no-writes flags, because the owner permits precisely documented unsupported flags and firn currently has no script-flag admission contract, instead of running a flagged script with legacy OOM semantics ([step-2 scope](../../research/investigations/memory-limit/README.md#step-2-implementation-record)).

Decision: The strings' metatable is read-only, so a script that writes a field of it gets Redis's read-only table error, as Redis does since its fix for CVE-2025-46818 in 7.2.11 and 7.4.6, because a field a script kept there would stay in one engine of the pool, while Redis 7.0.15's one Lua state shows it to every later script (Firn-wf probe run 38223467544), and Halo offers no way to share or move a table between engines, instead of Redis 7.0.15's writable metatable, which carries that published vulnerability, or the host copying the table between engines, which cannot carry functions and would rebuild a shared heap outside Halo. Reopen if Halo gains state that engines share and an application is found to depend on 7.0.15's writable metatable.

Rejected:
- An exact layout-preserving snapshot: rejected because no firn command observes collection layout through a cursor or guaranteed result; random choices need not reproduce Redis's dictionary layout, ordinary rehash already changes them, and abandoned picks are unpublished, so exact backing preservation adds no current compatibility guarantee. Reopen if a collection cursor or layout-dependent guarantee is added ([grounds](../../research/investigations/script-engines/README.md#logical-collection-restore)).
- Freezing expiry checks alone, as Redis 7.0.15 does: rejected because Redis moved to one time for the whole execution unit in 7.2, and following 7.0.15 would carry a live clock into every command part for a difference seen only while a script runs long.
- Releasing the statement around each of a script's commands: rejected because another client's command could then come between them, which Redis does not allow.
- A registry of scripts per connection: rejected because EVALSHA on one connection must find a script another loaded, as Redis's registry is the server's.
- Engines with independent library settings or random state: rejected because Redis shares one Lua state across scripts; the any-idle-engine pool shares one canonical copy of that state, which removes the ground for rejecting pools categorically.
- Engines owned by drivers, a script using its own driver's engine: rejected because Whitefoot does not expose which driver a context runs on, nor a lease that keeps a context on one driver while it waits, and a pool of the driver count's size removes the single-engine wait without that affinity.
- Answering NOSCRIPT to a script whose later attempt needs its source after a FLUSH: rejected because Redis 7.0.15 cannot apply SCRIPT FLUSH while a script runs, waiting below its busy threshold and answering BUSY above it, so once a script has first taken an engine, FLUSH waits for it until it ends, including between attempts; only an EVALSHA whose FLUSH came after its registry check and before it first took an engine can answer NOSCRIPT because of that FLUSH, as if the FLUSH came first.
- Copying the source at the check on every call: rejected because cache hits need no source copy, and that copy took 2.8 to 3.8% of firn's CPU under rate-limiter-flexible's script ([profile](../../research/investigations/deployment-performance/README.md#result)); waiting for running scripts before FLUSH preserves their later attempts without that copy.
