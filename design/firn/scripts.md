Decision: EVALSHA checks that the registry holds the script's SHA1 before it takes the engine, answering NOSCRIPT there as Redis 7.0.15 does, and, for each attempt whose engine has not compiled that SHA1, reads the registry again and copies the script's source from that read, while an attempt whose engine has compiled it copies nothing, because an engine whose generation is current compiled only scripts registered in that generation, EVAL and SCRIPT LOAD registering a script before they return the engine and EVALSHA compiling only a source it has just read from the registry under the current generation, and only SCRIPT FLUSH, which advances the generation, removes a registered script, so a cache hit never runs a script the registry did not hold when that engine was taken, while copying the source on every call took 2.8 to 3.8% of firn's CPU under rate-limiter-flexible's script ([profile](../../research/investigations/deployment-performance/README.md#result)), instead of copying the source at the check on every call; SCRIPT FLUSH waits until no script is in progress, as Redis 7.0.15 does below its busy threshold, instead of interrupting a running script's later attempts; only an EVALSHA whose FLUSH came after its registry check and before it first took the engine can answer NOSCRIPT because of that FLUSH, as if the FLUSH came first; its first take counts it in progress and records the kills count atomically with reading the generation and taking the engine, so once a script has first taken the engine, FLUSH waits for it until it ends, including between attempts.

Rejected:
- An exact layout-preserving snapshot: rejected because no firn command observes collection layout through a cursor or guaranteed result; random choices need not reproduce Redis's dictionary layout, ordinary rehash already changes them, and abandoned picks are unpublished, so exact backing preservation adds no current compatibility guarantee. Reopen if a collection cursor or layout-dependent guarantee is added ([grounds](../../research/investigations/script-engines/README.md#logical-collection-restore)).
- Freezing expiry checks alone, as Redis 7.0.15 does: rejected because Redis moved to one time for the whole execution unit in 7.2, and following 7.0.15 would carry a live clock into every command part for a difference seen only while a script runs long.
- Releasing the statement around each of a script's commands: rejected because another client's command could then come between them, which Redis does not allow.
- A registry of scripts per connection: rejected because EVALSHA on one connection must find a script another loaded, as Redis's registry is the server's.
- Engines with independent library settings or random state: rejected because Redis shares one Lua state across scripts; the selected future any-idle-engine pool must synchronize that state, which removes the ground for rejecting pools categorically.
- Answering NOSCRIPT to a script whose later attempt needs its source after a FLUSH: rejected because Redis 7.0.15 cannot apply SCRIPT FLUSH while a script runs, waiting below its busy threshold and answering BUSY above it, so once a script has first taken the engine, FLUSH waits for it until it ends, including between attempts; only an EVALSHA whose FLUSH came after its registry check and before it first took the engine can answer NOSCRIPT because of that FLUSH, as if the FLUSH came first.
- Copying the source at the check on every call: rejected because cache hits need no source copy, and that copy took 2.8 to 3.8% of firn's CPU under rate-limiter-flexible's script ([profile](../../research/investigations/deployment-performance/README.md#result)); waiting for running scripts before FLUSH preserves their later attempts without that copy.
- Writing a raised error's text raw, as Redis 7.0.15 does: rejected because no client reads such a reply as one error, so following 7.0.15 there keeps no compatibility and leaves the reply splitting Redis 7.2.13 fixed.
