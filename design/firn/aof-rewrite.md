Decision: firn keeps Redis 7.0.15's multi-part append-only layout below `appendonlydir`, with appendfilename `F` naming `F.<n>.base.aof`, `F.<n>.incr.aof`, `F.manifest` and `temp-F.manifest`, persisting the manifest by syncing the temporary file, renaming it and syncing the directory, because the manifest can select a consistent base and the incremental files that follow it while later writes continue, instead of one file whose replacement must also copy concurrent writes ([design](../../research/investigations/aof-rewrite/README.md#design)).

Decision: The rewrite replays the base and closed incremental files into a private keyspace and writes that dataset while the writer appends later commands to a new incremental file, because the closed log defines the exact state before that incremental file even for non-idempotent commands, instead of stopping the live keyspace for a complete scan (candidate B), tracking scan position and duplicating writes (C), or adding a runtime copy-on-write snapshot (D) ([candidates](../../research/investigations/aof-rewrite/README.md#candidates)).

Decision: Before publishing a switch manifest, the writer reads the current incremental file through replay into a private keyspace and, if it ends inside an unfinished block, cuts before the first MULTI following the last EXEC that closed a block, then syncs the file, because a closed file must replay whole once it is no longer last. This removes exactly the unfinished region replay leaves unapplied and leaves the live keyspace unchanged, instead of using an offset saved at startup, which goes stale when an appended transaction closes the block, or cutting before the latest MULTI, which leaves an earlier unfinished block when MULTIs are nested ([replay rules](append-only-file.md), [boundary reasoning](../../research/investigations/aof-rewrite/README.md#switch-time-block-boundary)).

Decision: Manifest serialization also encloses filenames containing apostrophes in double quotes, with apostrophes left literal inside them, because Redis 7.0.15's sdssplitargs reads that sdscatrepr encoding back, instead of copying sdsneedsrepr's omission of apostrophes and writing a manifest that the loader refuses. This deliberately differs from Redis's manifest writer.

Decision: The rewrite's temporary base is `temp-F.base` inside `appendonlydir`, using Redis's temporary append-only naming convention of `temp-`, appendfilename `F` and a suffix, because the installation rename must stay on one file system and distinct appendfilenames need distinct temporary base names, instead of Redis's rewrite-child PID name in the working directory or a sequence shared by independent manifests. Servers with the same appendfilename in one directory already share a manifest and are unsupported, as in Redis. This does not isolate temporary names from another dataset's upgraded base named literally `temp-F.base`; shared directories with that overlap remain unsupported until Whitefoot supplies exclusive creation ([limitation](../../docs/todo.md#whitefoot-requirements)).

Decision: Base files contain commands in Redis's append-only format, because firn reads and writes no RDB, instead of Redis's default RDB base preamble.

Decision: An old-style file `F` is upgraded by persisting a manifest naming it as base sequence 1 and then moving it from the working directory into `appendonlydir` with `std::fs::move_file`, because that order supports Redis's interrupted-upgrade recovery without copying the log, instead of a copied second file or interpreting an unfinished move as an empty dataset.

Decision: Manifest rename publishes the new selection even if its following directory sync fails: keep the new manifest in force, every published file and its history entries, and report failure in aof_last_bgrewrite_status; only a successfully synced install manifest permits history cleanup, whose failure cannot roll back the base, because Redis 7.0.15's writeAofManifestFile can fail after rename but backgroundRewriteDoneHandler then unlinks the new base the visible manifest may name, instead of copying that unlink and leaving an unreplayable manifest. Startup likewise syncs appendonlydir before deleting loaded history and retains every history entry if that sync fails, because loading an unchanged manifest does not establish its durability. When directory sync succeeds, cleanup follows Redis's active-manifest replacement before aofDelHistoryFiles, whose failure does not fail the rebuild.

Decision: BGREWRITEAOF with appendonly off answers Redis 7.0.15's generic rewrite-start failure, because a rebuild from closed logs has no source without an open append-only log and firn has no snapshot, instead of reporting an unknown command or claiming a rewrite started. This differs from Redis's ability to rewrite its live dataset with appendonly off ([remaining compatibility work](../../docs/todo.md#server)).

Decision: Installation and accepting a shutdown request are ordered by a metadata flag acquired together with the shutdown state: a request accepted first cancels installation, while a request arriving after installation starts waits until it ends, because Redis's event loop also completes its synchronous install handler before running SHUTDOWN and filesystem operations cannot run inside Whitefoot atomic statements, instead of allowing shutdown acceptance to race the install manifest's publication.
