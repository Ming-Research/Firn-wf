Decision: firn keeps Redis 7.0.15's multi-part append-only layout below `appendonlydir`, with appendfilename `F` naming `F.<n>.base.aof`, `F.<n>.incr.aof`, `F.manifest` and `temp-F.manifest`, persisting the manifest by syncing the temporary file, renaming it and syncing the directory, because the manifest can select a consistent base and the incremental files that follow it while later writes continue, instead of one file whose replacement must also copy concurrent writes ([design](../../research/investigations/aof-rewrite/README.md#design)).

Decision: A rewrite observes bounded live-map steps after S0, journals each mutating statement's complete after-images or, for an ordinary one-key command statement on a key already journaled in the window, its append-only bytes, and reconciles them in increasing sequence after the scanned base at S1, because a replacement image taken after each key's first write in the window, followed by every later write in order, restores the state at S1 exactly, while the rewrite's memory allocations fit an explicit reserve reported in process memory but excluded from maxmemory as its capture child node defines and its journal streams to a temporary file (owner rulings firn-q-rw-cut A, firn-maxmem-scope B and firn-q-rw-pace A; the rewrite-memory ruling firn-q-rw-memory-excluded A narrows B so that this reserve stays outside maxmemory), instead of rebuilding a private replay keyspace, which holds a second copy of the dataset ([protocol](../../research/investigations/aof-rewrite/scan-log.md#cut-and-authoritative-files)).

Decision: The sole writer rotates once at S1, atomically disabling capture, freezing journal staging and sealing collecting bytes through S1 under Meta, then drains the frozen journal to disk and drains and syncs the ordinary AOF prefix before publishing the new increment while keeping all old files named, because base(S1) must be paired only with commands after S1 to apply non-idempotent writes exactly once, instead of rotation at S0 or a separate counter read and byte-buffer exchange. A sealed file that ends inside a block, which only a startup-retained MULTI leaves, is cut before that block's first MULTI before publication, because base(S1) is the live dataset, which holds the writes appended inside the block and never applied the block itself, as Redis 7.0.15's BGREWRITEAOF writes its live dataset, instead of refusing the rewrite until a restart ([boundary](../../research/investigations/aof-rewrite/scan-log.md#stage-2-implementation)).

Decision: The writer retains the current increment's syntax and first-unclosed-MULTI boundary from startup's parser after its prescribed truncation, advances it from completed append outcomes with the shared syntax parser and block classification, preserves it after successful append rollback, and updates it immediately on switch truncation or published handle replacement, because validation at S1 must not suspend ordinary draining for work proportional to accumulated history, instead of rereading every healthy increment at the switch. An append or truncation outcome that cannot establish the exact state invalidates it; only that exceptional path uses the existing charged, cancellable syntax-only reread and refreshes the state on success. No commands execute during boundary tracking, no history is retained in memory, and S1 ordering and rotation-backlog charges remain unchanged ([attribution and invariant](../../research/investigations/aof-rewrite/scan-pace.md#switch-validation-under-continuous-writes)).

Decision: Manifest serialization also encloses filenames containing apostrophes in double quotes, with apostrophes left literal inside them, because Redis 7.0.15's sdssplitargs reads that sdscatrepr encoding back, instead of copying sdsneedsrepr's omission of apostrophes and writing a manifest that the loader refuses. This deliberately differs from Redis's manifest writer.

Decision: The rewrite's temporary base is `temp-F.base` inside `appendonlydir`, using Redis's temporary append-only naming convention of `temp-`, appendfilename `F` and a suffix, because the installation rename must stay on one file system and distinct appendfilenames need distinct temporary base names, instead of Redis's rewrite-child PID name in the working directory or a sequence shared by independent manifests. Servers with the same appendfilename in one directory already share a manifest and are unsupported, as in Redis. This does not isolate temporary names from another dataset's upgraded base named literally `temp-F.base`; shared directories with that overlap remain unsupported until Whitefoot supplies exclusive creation ([board item `firn-wf-excl-create`](https://claude.ai/artifact/7tocXS3iUdthCLCQCMd3ip)).

Decision: Base files contain commands in Redis's append-only format, because firn reads and writes no RDB, instead of Redis's default RDB base preamble.

Decision: An old-style file `F` is upgraded by persisting a manifest naming it as base sequence 1 and then moving it from the working directory into `appendonlydir` with `std::fs::move_file`, because that order supports Redis's interrupted-upgrade recovery without copying the log, instead of a copied second file or interpreting an unfinished move as an empty dataset.

Decision: A rewrite's manifest rename whose directory sync then fails with an error other than EINVAL fails the attempt and saves that error as the AOF sync error, so writes are refused with MISCONF until a recovery rewrite's installation is durable, as after a failed sync of the active file, because the device confirmed neither the rename nor the entries it names and a restart may read either manifest, instead of Redis 7.2.16, which only fails the rewrite and keeps acknowledging writes (aof.c:572-588,821-823,2443-2446); this deliberately differs from Redis ([Redis's behaviour](../../research/investigations/aof-rewrite/rewrite-faults.md#switch-manifest-whose-directory-sync-fails)). EINVAL, which means the filesystem cannot sync directories at all, counts as a successful sync, as Redis's fsyncFileDir treats it (util.c), so the attempt completes and writes continue on the new increment: a failure that never clears would leave every rewrite unfinished and the append-only file growing without bound. The rule covers every manifest publication, startup's included; a startup whose following directory sync returns EINVAL skips its history cleanup and keeps every history entry, which is harmless because the next installation's cleanup removes them. On a failure other than EINVAL at the switch the old manifest and append handle stay in force and the new increment stays in place, as Redis's openNewIncrAofForAppend cleanup does (aof.c:850-855), because both manifests name the old increment and only the renamed one names the new, so writes kept on the old handle are in whichever selection a restart reads, instead of adopting the new increment, whose writes a restart reading the old manifest loses. At installation the renamed manifest stays in force with every published file and its history entries, and only a successfully synced install manifest permits history cleanup, whose failure cannot roll back the base, because both manifests name the active increment and Redis 7.0.15's backgroundRewriteDoneHandler unlinks the new base the visible manifest may name, instead of copying that unlink and leaving an unreplayable manifest. Startup likewise syncs appendonlydir before deleting loaded history and retains every history entry if that sync fails, because loading an unchanged manifest does not establish its durability. When directory sync succeeds, cleanup follows Redis's active-manifest replacement before aofDelHistoryFiles, whose failure does not fail the rebuild.

Decision: BGREWRITEAOF with appendonly off answers Redis 7.0.15's generic rewrite-start failure, because this experiment retains the existing appendonly-off behavior and its publication protocol requires an authoritative increment, instead of reporting an unknown command or claiming a rewrite started. This differs from Redis's ability to rewrite its live dataset with appendonly off ([board item `firn-bl-01-29`](https://claude.ai/artifact/7tocXS3iUdthCLCQCMd3ip)).

Decision: Installation and accepting a shutdown request are ordered by a metadata flag acquired together with the shutdown state: a request accepted first cancels installation, while a request arriving after installation starts waits until it ends, because Redis's event loop also completes its synchronous install handler before running SHUTDOWN and filesystem operations cannot run inside Whitefoot atomic statements, instead of allowing shutdown acceptance to race the install manifest's publication.

Decision: An append-only file or manifest whose name is a symbolic link is refused where Redis 7.0.15 follows the link, provisionally, because firn opens names below a directory through Whitefoot's operations, which refuse a link at the name so that a name stays below its root, and no deployment is known to keep these files behind a link, instead of adding to Whitefoot now an operation that follows a link with the authority it reaches; reopened when a deployment keeps its file behind a link ([board item `firn-bl-03-00`](https://claude.ai/artifact/7tocXS3iUdthCLCQCMd3ip)).


Rejected:
- Adopting the switch's new increment after its manifest's directory sync fails, with writes still acknowledged (superseded): rejected because a restart that reads the old manifest, which a rename lost before reaching the device leaves, does not replay that increment, so writes acknowledged and synced into it are lost.
- Full-history reread at every S1 switch: rejected because the 14900K sample [run 38379619656](https://github.com/Ming-Research/Firn-wf/actions/runs/38379619656) finished scanning but aborted with rotation_reserve while rereading; accounting reconstructs the failing collecting-buffer expansion as 4 MiB to 8 MiB at R = 16 MiB. Redis 7.2.16 does not reread the old increment at its switch ([observation and reconstruction](../../research/investigations/aof-rewrite/scan-pace.md#switch-validation-under-continuous-writes)).
- Private replay in the rewrite worker (superseded): rejected because it retains an eager second copy of the dataset, which the bounded rewrite reserve R cannot hold; the owner's firn-maxmem-scope B ruling (maxmemory governs process footprint) also rejects it, which firn-q-rw-memory-excluded A narrows without lifting.
- Private replay for switch-time block validation (superseded): rejected because it too would rebuild a second copy of the dataset before the switch; syntax and block classification require no reconstructed keyspace.
- Replaying scan-window commands after fuzzy images without a journaled image of each key first: rejected because a scanned image can already include a later write, so INCR and collection changes can then apply twice; a key's commands are replayed only after its first write in the window journaled a complete image.
- Failing the rewrite without saving a sync error after EINVAL from the manifest's directory sync: rejected because EINVAL means this filesystem cannot sync directories at all, so every rewrite would fail the same way and the append-only file would grow without bound; writes still continue, so the cost is unbounded growth, not lost data.
- Failing the rewrite, saving the error and refusing writes with MISCONF after EINVAL from the manifest's directory sync: rejected because the recovery rewrite's directory sync returns EINVAL too, so the refusal would never clear and the append-only file could not be written again; Redis 7.2.16's fsyncFileDir treats EINVAL as success.
- Refusing the rewrite while a startup-retained MULTI remains: rejected because every write appended after that MULTI is then lost at the next restart, where Redis's live rewrite keeps them.
