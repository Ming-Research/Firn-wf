Decision: firn's EXEC runs queued commands in order through their shared implementations, in one atomic statement naming every key, the keyspace's metadata and the live-client table needed by CLIENT, with the time of the connection read containing EXEC for all commands and file records wrapped in MULTI and EXEC when they are more than one command, because Redis lets no other client's command come between them, freezes one time for EXEC and propagates a transaction whole, instead of running each queued command in its own statement ([command-parts](command-parts.md)). The client-table uses are conditional, but the pinned compiler also acquires it on clean EXEC without CLIENT: using the later Meta lock group takes the earlier ClientTable group ([ordered acquisition](https://github.com/Ming-Research/Whitefoot/blob/d75f318d56318834785322bde3a3656fb93116a6/compiler/src/lowering/builder/atomic.rs#L353)). Conditional acquisition is therefore not an implemented performance guarantee.

Decision: admission identifies a command and checks its table arity before authentication and eviction, refuses unknown subcommands immediately and dirties an open transaction, refuses an unknown name outside a transaction, and refuses SHUTDOWN before queueing because Redis 7.0.15 processCommand performs those checks before its OOM decision and marks SHUTDOWN CMD_NO_MULTI; inside a transaction a name firn does not identify, like a known command lacking command parts, is queued and makes EXEC refuse the whole transaction without running any of it, because firn cannot tell a name Redis lacks from a Redis command it does not run, and refusing such names when sent again left Redis's own test suite inside a transaction and turned 94 passing tests into failures ([run 37904672454](https://github.com/Ming-Research/Firn-wf/actions/runs/37904672454)), instead of refusing every unidentified name when sent ([command-parts](command-parts.md)).

Decision: A transaction queues at most 1 GiB of arguments, and as many arguments and commands, a command past it refused when sent so that EXEC aborts the transaction, because the queue's spaces grow no further than 2^30 elements and a command that does not fit whole cannot be queued, where Redis 7.0.15 bounds no transaction's queue by default; a provisional limit, since the selected consumers queue one to five small commands in a transaction ([consumers](https://github.com/Ming-Research/Firn-wf/blob/fab3ed5b411f61bd2f8eb85f4a2c29f4582f4a91/research/investigations/consumers/README.md#what-the-milestone-needs-from-firn)) and no other workload has been measured, reopened when one queues more, instead of queueing past the limit, which would cut the command's arguments.

Decision: A connection's transaction is kept apart from its client record and passed with it to each command, because EXEC reads the queued commands while their replies are written into the client record, instead of keeping the queue inside the client record.

Decision: EXEC runs supported CLIENT subcommands through the same non-waiting implementation as the network path and passes the total queue length for reporting, because Redis 7.2.16 queues these subcommands, whose [command descriptors](https://github.com/redis/redis/tree/7.2.16/src/commands) omit NO_MULTI, and runs them in [execCommand](https://github.com/redis/redis/blob/7.2.16/src/multi.c#L195), instead of refusing their transaction with EXECABORT. Their NOSCRIPT restriction remains the [script-admission decision](command-parts.md).

Decision: EXEC publishes changed connection records before its atomic statement completes, because another connection must not observe new keys with old connection facts, instead of publishing the records afterward in the network loop.

Decision: A persistence-refused WRITE command or PING dirties an open MULTI, and EXEC aggregates queued WRITE flags and discards a writing queue with EXECABORT plus the shared MISCONF text before its ordinary dirty-queue check, rechecking under the execution's Meta hold, because Redis 7.0.15 server.c:3568-3576,3735-3740,3881-3905 and multi.c:85-87,105-109,136-140,170-178,229-233 order admission this way, instead of executing writes from a previously healthy queue or denying read-only EXEC; accepted queued PING does not make EXEC a WRITE command and members do not repeat ordinary admission inside EXEC ([investigation](../../research/investigations/aof-write-errors/README.md#question-and-reference)).

Rejected:
- Refusing a transaction containing supported CLIENT subcommands with EXECABORT: rejected because Redis 7.2.16's CLIENT subcommand descriptors omit NO_MULTI and execCommand executes each queued command; refusing the whole transaction loses the replies and connection changes Redis applies.
- Queueing every known command and running those without parts outside the statement: rejected because such a transaction is no longer atomic, which is what the selected consumers rely on.
- Refusing a command without parts, or a name firn does not identify, when it is sent: rejected because a client that stops at the error never reaches EXEC and stays inside the transaction ([run 37461272313](https://github.com/Ming-Research/Firn-wf/actions/runs/37461272313), [run 37904672454](https://github.com/Ming-Research/Firn-wf/actions/runs/37904672454)).
- WATCH and UNWATCH now: rejected because no selected consumer sends them; WATCH inside a transaction is refused as Redis refuses it.
