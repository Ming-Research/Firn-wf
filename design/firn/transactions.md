Decision: firn's EXEC runs a transaction's queued commands in order by their command parts, in one atomic statement holding every key and the keyspace's metadata, with the one time EXEC is given, the instant serve read the connection's input as for every command of that read, and their file records wrapped in MULTI and EXEC when they are more than one command, because Redis 7.0.15 lets no other client's command come between a transaction's commands, freezes one time for the commands nested in EXEC, and propagates a transaction so, and the parts are the implementation scripts share with the network path ([command-parts](command-parts.md)), instead of running each queued command through the network path in a statement of its own.

Decision: A command a transaction cannot run by its parts is queued and answered QUEUED, and EXEC then refuses the whole transaction with an EXECABORT error saying firn does not run one of its commands in transactions, nothing of it run, while a command it can run is checked for its arity when sent, as Redis checks it, because firn names its commands only in the dispatcher's rows and cannot tell an unknown name from a command without parts, and a refusal when the command is sent left clients that stop at an error reply, Redis's own test suite among them, inside the transaction, which turned 144 of the suite's later tests into refusals ([run 37461272313](https://github.com/Ming-Research/Firn-wf/actions/runs/37461272313)), instead of refusing such a command when it is sent.

Decision: A transaction queues at most 1 GiB of arguments, and as many arguments and commands, a command past it refused when sent so that EXEC aborts the transaction, because the queue's spaces grow no further than 2^30 elements and a command that does not fit whole cannot be queued, where Redis 7.0.15 bounds no transaction's queue by default; a provisional limit, since the selected consumers queue one to five small commands in a transaction ([consumers](https://github.com/Ming-Research/Firn-wf/blob/fab3ed5b411f61bd2f8eb85f4a2c29f4582f4a91/research/investigations/consumers/README.md#what-the-milestone-needs-from-firn)) and no other workload has been measured, reopened when one queues more, instead of queueing past the limit, which would cut the command's arguments.

Decision: A connection's transaction is kept apart from its client record and passed with it to each command, because EXEC reads the queued commands while their replies are written into the client record, instead of keeping the queue inside the client record.

Rejected:
- Queueing every known command and running those without parts outside the statement: rejected because such a transaction is no longer atomic, which is what the selected consumers rely on.
- Refusing a command without parts when it is sent, as Redis refuses an unknown one: rejected because a client that stops at the error never reaches EXEC and stays inside the transaction.
- WATCH and UNWATCH now: rejected because no selected consumer sends them; WATCH inside a transaction is refused as Redis refuses it.
