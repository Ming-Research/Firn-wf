Decision: A shutdown request stays recorded in the server's state and its requesting context fires the current receive wake generation and a separate shutdown cancellation state watched by main, the signal context and the expiry context, because CONFIG timeout changes must wake receives without ending accept, signal or expiry waits, instead of making all contexts follow replaceable receive generations; the accept wait has no deadline and the expiry sleep ends on shutdown cancellation. Network command dispatch returns whether it accepted SHUTDOWN after recording the request and firing the receive generation, because its caller can then fire its separate shutdown source without reacquiring server state. The request stays separate from Meta.stopping, and main stops the append-only writer only after every client has gone, because a command already running may still append records before its context ends. A send keeps its never-firing watch and existing one-second deadline logic, because cancelling it would additionally truncate replies that firn currently sends; Redis 7.0.15 promises no flush of ordinary client replies at exit ([send reasoning](../../research/investigations/orderly-stop/README.md#pending-client-replies)). Scripts and guarded waits for their engine remain outside host cancellation ([script execution](scripts.md)).

Decision: Shared server state owns the current receive wake generation's cancellation source; each CONFIG SET timeout that changes the idle limit replaces the source in the same atomic statement as the limit, takes the old source out and fires it after that statement, while shutdown records its request and retains the current source together before firing it outside the statement, because Whitefoot v0.119 makes the shared handles droppable and cancel_fire waits, instead of using a receive deadline of at most a second to observe CONFIG changes. A client caches its generation watch, receives without a deadline at timeout zero or with the remaining idle interval otherwise, and re-reads shutdown and the limit after cancellation or a deadline; while running it replaces a fired watch with the current generation's watch and waits again unless the current limit has expired, because a fired generation has already been replaced unless shutdown was requested. A generation awaiting its fire still wakes its old watches when that fire completes, so overlapping CONFIG changes or shutdown cannot strand a client on an unfired stale watch. Dropping replaced watches and fired sources releases their handles, and server teardown releases the final source, because each watch independently retains its state ([lifecycle and pending measurement](../../research/investigations/orderly-stop/README.md#live-idle-limit-updates)).

Decision: `SHUTDOWN SAVE` takes Redis 7.0.15's failed-save path, refused unless FORCE is given, because firn writes no snapshot, instead of ignoring SAVE or answering a syntax error.

Decision: SIGTERM and SIGINT request the orderly stop SHUTDOWN requests through one stop listener that main opens just before it listens and a context of its own waits on without a deadline, because Redis 7.0.15 shuts down gracefully on either under its default shutdown-on-sigterm and shutdown-on-sigint, appending and syncing its append-only file, and the shared shutdown watch ends the signal wait when another context requests shutdown, instead of polling the request every tenth of a second. Main records and fires its own request after the last client leaves when it stops for another reason, including the client limit. Cancellation closes the listener without requesting shutdown again; a host that refuses the listener stops firn with status 3, as an address it cannot listen on does, instead of serving without the graceful stop.

Decision: On its first signal the context closes its listener before recording the request, restoring the host default, so that any later SIGTERM or SIGINT ends firn at once, because the only way Whitefoot gives a program to end without joining its contexts is the host default, and closing first keeps Redis's escape from a stop that does not finish, a second SIGINT, even while the request waits behind a script that holds the keyspace, instead of keeping the listener through the drain, which would ignore a second SIGTERM as Redis does but leave nothing short of SIGKILL to end firn. A second SIGTERM thus ends firn where Redis ignores it, and a second SIGINT ends it by the signal where Redis exits with status 1.

Rejected:
- A receive deadline of at most a second to observe CONFIG changes: rejected because it arms timers and wakes unlimited idle clients periodically, while replaceable wake generations deliver live limit changes directly without polling.
- Propagating shutdown only by polling deadlines: rejected because it cannot end a wait without a deadline, arms a timer for each parked receive and delays exit until the next poll; v0.110 cancellation can end those host waits directly.
