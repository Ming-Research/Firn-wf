Decision: A failed list lookup and FIFO registration share one whole-keyspace, metadata and event-hub hold, and the producer services ready registrations after committing its entire command, EXEC or accepted script and before releasing that hold, because original-key rescanning, FIFO allocation and move chains must precede competing consumers, instead of waking connection owners to race for values. Readiness follows Redis 7.2.16 dbAdd for newly installed lists; SET, deletion and a replacement with another type do not wake list waiters. A list producer that creates a list on a key where a client waits, list-capable RENAME/COPY and every list write of a promoted connection run under the broader hold through the held command parts, with their effects staged and copied into the log as the [append-only file](append-only-file.md) records; every other list write holds only its own keys, as the next decision says, and ordinary GET/SET do not gain a shared target or registry lookup ([service boundary](../../research/investigations/firn/blocking-lists.md#service-boundary)).

Decision: A top-level list write holds only its keys' entries and the metadata and appends its bytes in place, as before blocking lists existed, unless it creates a list on a key where a blocked client waits. LINSERT, LPUSHX and RPUSHX never create a list; LPUSH and RPUSH create none when their key holds a live list; LMOVE and RPOPLPUSH create none unless the source holds a live list and the destination holds nothing or an entry whose expiry has passed (a destination holding another kind is refused). A push or a move that would create a list also takes the event hub, after its own entries, and asks the registry whether a client waits on that key; only if one does it leaves and runs under the whole-keyspace hold of the previous decision. RENAME, RENAMENX and COPY, and every list write of a promoted connection, always run under that hold. This is sound because a client waits only on a key that holds no live list, where its failed lookup registered it, a registration holds the whole keyspace and so excludes every entry hold, and only the creation of a list there makes a client ready: while a write holds the entry of the key it creates, nobody can start waiting on that key, and a write to a live list, or a creation where nobody waits, wakes nobody, instead of holding the whole keyspace for every list write or for every write that creates a list. The test is a live list and not an existing key: a blocked client stays registered on a key that a string with an expiry has taken, and a push after that expiry replaces the string with a new list and makes the client ready ([producer holds](../../research/investigations/firn/blocking-lists.md#producer-holds)). The registry check is provisional until the remeasurement of the head shows no creating write wholly slower than the version without blocking lists; reopen the choice if one is.

Decision: Pending list requests extend the existing connection event hub and promote a connection on its first actual suspension, retaining original arguments, distinct key memberships and a never-reused request generation, because receive-side EOF, independent output and cancellation already have one owner there, instead of adding a second socket lifecycle. Fewer than 2^64 waits per process is the supported generation bound. Ready service, CLIENT UNBLOCK, timeout and disconnect remove all memberships under the hub before completion can be observed; only a service that wins this transition consumes data. A promoted CLIENT UNBLOCK requester also commits its confirmation before releasing the hub, because a publication by the released target is causally later than that confirmation ([ownership](../../research/investigations/firn/blocking-lists.md#ownership)).

Decision: Pending requests retain owned arguments, connection/protocol identity, deadline, memberships and scalar random/peak continuation, while the suspended command owner retains its Client and actual service uses a temporary Client adapter, because pending arbitration needs no reply workspace, session configuration or process meter and completed retries must return the connection's evolving random state before its pipeline continues, instead of retaining a second Client throughout suspension. The serving adapter obtains fresh settings/time and a share of the producer's process-wide meter; reply and continuation commit together to the existing live connection record, and cancellation drops both. This ownership choice stands independently of heap alignment support; fewer retained idle allocations trade against adapter allocation on each retry, with no measured memory or throughput claim ([request and continuation ownership](../../research/investigations/firn/blocking-lists.md#request-and-continuation-ownership)).

Decision: Each resumed command repeats current memory and persistence admission under the producer's hold, including ServerState for current settings, and finite-maxmemory service with pending waiters waits for an active AOF rewrite before entering that hold, because rewrite cleanup cannot finish while its waiter holds Meta and producer allocations can change admission, instead of skipping replay eviction or releasing the value-allocation boundary to wait. This deliberately adds rewrite latency to those list-service units; physical map-node retention can increase eviction and remains an unmeasured acceptance risk, so no general equality of maxmemory outcomes is claimed ([admission cost](../../research/investigations/firn/blocking-lists.md#admission-cost)).

Decision: Timeout conversion stays behind one explicit incomplete boundary pending firn-req-extended-float, because neither exact decimal ceiling nor binary64 reproduces Redis's separately rounded extended parse and multiplication, instead of silently accepting incompatible finite deadlines. Canonical literal 0 alone supplies the implemented infinite wait; indexed absolute deadline storage and cancellable one-shot service are prepared for the complete converter, without periodic polling or a claim of forward wall-clock-jump parity ([numeric counterexample](../../research/investigations/firn/blocking-lists.md#numeric-counterexample)).

Rejected:
- Holding the whole keyspace, metadata and event hub for every top-level list producer, the first version of this node: rejected because on two server CPUs it ran LPUSH, RPUSH, LINSERT and LMOVE at 0.31 of the rate without it at pipeline depth 16, with about half the cycles in the whole-keyspace hold, though a write to a live list cannot make a client ready ([measurement](../../research/investigations/firn/blocking-lists-performance.md#a1-cost-on-existing-commands-append-only-file-off)).
- Holding the whole keyspace, metadata and event hub for every top-level list write that can create a list, the second version of this node: rejected because on two server CPUs a push that creates its list ran at 0.313 of the rate without it at pipeline depth 16 and 0.801 at depth 1, with 38.8% of the cycles in the whole-keyspace hold, though a creation on a key where no client waits cannot make anyone ready ([measurement](../../research/investigations/firn/blocking-lists-performance.md#a1-again-the-narrowed-hold-7a4e4de)).
