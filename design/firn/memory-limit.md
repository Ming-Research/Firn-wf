Decision: firn's used_memory counts Whitefoot's heap_in_use, the requested bytes of live allocations, with resident bytes reported separately and the maxmemory comparison subtracting firn's allocated pending append-only buffers, saturating at zero, because the owner-approved memory-statistics proposal supplies that actual heap measurement while Redis's usable-allocation count includes allocator rounding that this measurement does not expose, instead of claiming that the requested-byte count equals Redis's allocator-usable bytes ([counting proposal](../../research/investigations/memory-limit/README.md#proposals)).

Decision: firn supports all eight Redis 7.0.15 maxmemory policies, noeviction, allkeys-lru, allkeys-lfu, allkeys-random, volatile-lru, volatile-lfu, volatile-random and volatile-ttl, because their selection, refusal and reporting share machinery and the owner's ruling A on firn-maxmemory-policies selects Redis's complete policy interface, instead of restricting deployment to noeviction, allkeys-lru and volatile-lru ([policy comparison](../../research/investigations/memory-limit/README.md#proposals)).

Decision: every entry holds Redis's 24-bit LRU clock or LFU minute stamp and counter in one u32, initialized and refreshed on every lookup that Redis 7.0.15 refreshes under every policy, preserving LOOKUP_NOTOUCH and LFU overwrite semantics, because OBJECT IDLETIME is observable even under the default noeviction and the owner's ruling A on firn-access-stamp selects that behavior, instead of maintaining access metadata only while an LRU or LFU eviction policy is selected ([access-stamp comparison](../../research/investigations/memory-limit/README.md#proposals)).

Decision: access tracking uses memory settings read once per connection read beside its calendar clock, shared by every command of that read, queued commands run by EXEC and script calls across attempts, except for the connection's own CONFIG SET refresh below, because holding ServerState with every key statement serializes commands across cores and the draft showed roughly 7 to 10% loss on two CPUs at pipeline depth 16 in [Firn-wf run 37859919278](https://github.com/Ming-Research/Firn-wf/actions/runs/37859919278), while Redis's own policy switch leaves stale stamps that take time to adjust, instead of retaining the common hold or requiring a concurrent configuration-publication mechanism; a lookup racing CONFIG SET may write an old-policy stamp, and CONFIG GET/SET and INFO still access ServerState directly ([owner's snapshot ruling and measurement limits](../../research/investigations/memory-limit/step-1.md#recorded-outcome-settings-snapshot)).

Decision: an unwritten script attempt abandoned for its interpreter step budget restores every refreshed key's stamp to its value before that attempt's first refresh and restores firn's LFU random state before releasing the same atomic keyspace statement, using a first-refresh journal owned and dropped by the attempt environment, because Redis runs a script once and an abandoned attempt's LFU increments are ones Redis never makes, instead of accepting counter drift or holding the keyspace across attempts; completed attempts and attempts that wrote retain their stamps, and SCRIPT KILL remains reachable between attempts ([owner's retry ruling](../../research/investigations/memory-limit/step-1.md#recorded-outcome-script-retry-access)).

Decision: when maxmemory is set, each command's own context checks the limit before the command runs and evicts there, re-reading the heap before each victim, because firn runs independent commands in parallel and an ordering of every command's check and execution would serialize them whenever a limit is set, while the difference from Redis's single-threaded order is only a brief overshoot by the allocations of commands in flight and at most one extra eviction per concurrently evicting context, which Redis's own bounded eviction already permits in kind, instead of one dedicated evictor context or a command turn serializing admission through execution.

Decision: eviction samples maxmemory-samples eligible keys from a random map_scan cursor under a whole-map hold, keeping one shared pool of the 16 best LRU, LFU or TTL candidates in Meta and drawing random-policy victims uniformly from the gathered batch, because the owner's firn-evict-sampling A ruling requires Redis's candidate retention without refreshing stamps, and Meta already orders each removal with its AOF record while owned candidate names let deletion release the whole map, instead of first-returned random victims, per-context pools or a second shared pool object ([sampling and exhaustion](../../research/investigations/memory-limit/README.md#step-2-implementation-record)).

Decision: the per-read snapshot includes the limit, policy, sample count, tenacity and LFU parameters and is refreshed after this connection executes CONFIG SET before its remaining commands run, because the owner's firn-evict-config A ruling requires a pipelined setting to affect the following command while other connections keep the accepted snapshot boundary, instead of re-reading settings for every command or retaining this connection's old settings until another read.

Decision: mem_not_counted_for_evict is the sum of the collecting AOF buffer's capacity and the writer's private pending capacity published in Meta at allocation, swap, drain and suffix replacement, because the owner's firn-aof-exclusion A ruling requires allocated storage to stay excluded throughout a partial write and handoff, instead of excluding lengths alone or counting the same unwritten bytes while the writer owns them.

Decision: CONFIG RESETSTAT preserves the observed heap peak while resetting eviction counts, and maxmemory refusal inside MULTI rejects every command except EXEC, DISCARD, QUIT and RESET, with a queue-time OOM marking the transaction dirty for the generic previous-errors EXECABORT and only an OOM rejection at EXEC admission using the explicit OOM cause, because Redis 7.0.15 is the reply and statistics oracle, instead of retaining a separate queue-time OOM cause or restarting the lifetime peak ([transaction refusal](../../research/investigations/memory-limit/README.md#transactions-and-scripts), [statistics](../../research/investigations/memory-limit/README.md#settings-accounting-and-persistence)).

Decision: a resumable volatile-policy absence scan is invalidated by a flag in the expiry metadata set by queue_due in the same atomic statement that creates or transfers an expiry, while allkeys absence uses live map_count under the sampling hold, because a concurrent EXPIRE can otherwise create eligibility behind the cursor and cause false OOM, but invalidating on every WRITE lets plain permanent SETs restart an empty volatile scan forever, instead of per-command mutation markers, a second expires index or an unbounded whole-map absence sweep; expiry queue removal and FLUSH preserve the flag, and heap comparison shares the final sampling hold ([exhaustion proof](../../research/investigations/memory-limit/README.md#step-2-implementation-record)).

Rejected:
- Only noeviction, allkeys-lru and volatile-lru: rejected because the owner selected the complete eight-policy interface and the sampling, refusal and reporting machinery is shared.
- Refreshing the stamp only under LRU or LFU policies: rejected because OBJECT IDLETIME would report the wrong idle time under noeviction and the other non-LFU policies.
- Holding ServerState with each key statement: rejected because it introduces a shared serialization point across independent keys; the draft's two-CPU depth-16 loss exceeded its twin spread, while Redis already permits stale policy stamps.
- Requiring concurrent configuration publication before completing access tracking: rejected because the per-read snapshot meets the accepted policy-switch behavior without a new publication mechanism whose representation has not been selected.
- Accepting abandoned attempts' LFU drift: rejected because OBJECT FREQ can then report increments Redis's single script execution never performs.
- Continuing indefinitely after the first access refresh while holding the keyspace: rejected because a read-only infinite script could then permanently hold the keyspace and evade SCRIPT KILL, contradicting the approved retry design.
- One dedicated evictor context: rejected because its completion can go stale before the command runs, so it gives no closer order than each context evicting, and adds wake-ups and waiting.
- Serializing every command's check and execution while a limit is set: rejected because cache deployments set a limit and would lose parallel execution, against firn's goal of scaling the keyspace past two cores.
