Decision: firn stores a stream as Redis 7.2.16's t_stream.c structures it, in nodes kept in an ordered map keyed by each node's master ID: a node holds its master fields, its entries in ID order, deleted ones kept as tombstones, its live and deleted counts, and its size in bytes as Redis's listpack encoding would make it, because `~` trimming removes only whole nodes, so the replies of XLEN after `XADD ... MAXLEN ~` and of XTRIM depend on where every node starts, and these rules (a new node when the tail reaches stream-node-max-bytes or stream-node-max-entries, a node freed when XDEL removes its last live entry, `=` trimming marking tombstones inside one node) are then each written once and checked line by line against Redis's source, instead of an entry map with a separate node summary, treating `~` as `=`, or storing listpack bytes. Node sizes are computed from Redis's element encodings ([research record](../../research/investigations/firn/streams.md#node-layout)); a rewrite rebuilds nodes from the live entries, as Redis's command-form rewrite does.

Rejected:
- An ordered map of live entries with a second map summarizing each node: rejected because every write must change both maps and keep them describing the same entries, an invariant the node layout holds by construction, and finding an entry's node needs a second lookup.
- Treating `~` as exact trimming without nodes: rejected because XLEN and XTRIM's count after an approximate trim then differ from Redis 7.2.16's, failing eight cases of its own suite and the priority that replies match the reference.
- Storing each node's real listpack bytes: rejected because it needs the whole encoder and decoder and a decode on every read, while firn reads and writes no RDB file that would use those bytes.
