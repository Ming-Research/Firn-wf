Decision: Capture reserves R = floor(maxmemory / 20), or 16777216 bytes when maxmemory is zero, and excludes its charged memory from maxmemory without requiring spare service headroom, because a cache at its limit must remain able to rewrite and Redis 7.2.16 does not count its rewrite child in the parent's allocation counter, instead of admitting only when counted heap plus R plus max(R, 1048576) fits maxmemory. R remains a separate bound: budget exhaustion aborts capture, leaves client commands and ordinary AOF writes intact and reports aof_last_bgrewrite_status:err; sequence exhaustion, stopping and a reserve below the fixed charge plus one staging chunk still refuse admission ([cache-limit accounting](../../../research/investigations/aof-rewrite/scan-log.md#rewrite-at-the-cache-limit)).

Decision: Any unsuccessful attempt, whether refused at admission, aborted during capture or failed on host I/O, disables automatic rewrites until a manual attempt succeeds, because the owner's ruling A on firn-q-rw-limits excludes automatic retry so that persistent pressure cannot become a silent retry loop, instead of Redis 7.0.15's aofRewriteLimited, which keeps starting automatic rewrites and only delays them, from 1 up to 60 minutes, after three consecutive failures. This differs from Redis: after one failed attempt the AOF keeps growing until an operator runs BGREWRITEAOF. Recovery rewrites after a saved sync error are not automatic rewrites: they run and retry whatever this block, as the [append-only file](../append-only-file.md) decides.

Decision: For a statement that journals images, per-statement scratch coalesces complete owned replacement images before publishing one sequence-, length- and kind-framed unit into fixed 64-KiB staging chunks, because an EXEC or script must commit its final images with its normal effects and Meta counter while cleanup must release bounded owners, instead of borrowed entry descendants, a second exported keyspace, or recursively releasing an entire journal under Meta.

Decision: The sole AOF writer drains the bounded staging queue outside Meta to `temp-F.journal` in appendonlydir and the worker reconciles that file through one charged 64-KiB buffer after S1, because the owner's firn-q-rw-pace A ruling removes cumulative journal bytes from the memory reserve while atomic statements cannot wait or perform I/O, instead of retaining the complete journal in memory or replaying the ordinary incremental AOF without first after-images. R covers statement scratch, staging, in-flight draining, scan and readback buffers and rotation backlog; a record that cannot enter staging aborts with journal_backlog without blocking normal writes. The temporary journal is not authoritative and requires no fsync; existing base, incremental-file, manifest and directory sync obligations remain; close the journal handles and attempt removal after success or abort, and attempt removal of an unlisted leftover after manifest recovery on restart ([protocol and falsifiers](../../../research/investigations/aof-rewrite/journal-disk.md#proposed-design)).

Decision: Startup serves after authoritative AOF recovery even when removing an unlisted temporary journal fails, and the next rewrite must remove that old name before opening or truncating a new journal, because the temporary journal contributes no recovered state and Redis 7.0.15 likewise loads manifest-selected files while its temporary-file cleanup ignores unlink failure, instead of refusing service for a disposable leftover or silently truncating it on retry ([Redis recovery](https://github.com/redis/redis/blob/7.0.15/src/aof.c#L1634-L1715), [rewrite cleanup](https://github.com/redis/redis/blob/7.0.15/src/aof.c#L2502-L2510), [increment cleanup](https://github.com/redis/redis/blob/7.0.15/src/aof.c#L695-L702)). A failed pre-open removal refuses that rewrite with journal_io without modifying the old file; a manifest-listed name is protected.

Decision: An ordinary command statement holding exactly one key whose previous write lies inside the current rewrite window journals its own append-only bytes instead of the key's image, because that key's first write in the window already journaled a complete image and every later write is journaled in sequence, so replaying the statement's bytes reproduces the key, while a key that keeps growing during a rewrite would otherwise be copied whole on every write and exhaust R (owner card firn-q-rw-bigkey, option C), instead of retaining only the latest image per key, which still copies the key on every write. A key's first write in the window, and every statement holding several keys or the whole map, keep complete images: the scanned image of a key not yet observed can include later writes, and a multi-key statement's bytes can read keys whose replayed state is not yet exact, as SUNIONSTORE and COPY do. EXEC holds the whole map and keeps images; journaling its bytes needs the keys it reads, which firn does not track (status board item firn-bl-rw-exec-effect).

Decision: Scripts keep complete images even for one declared key, because complete-image capture is valid for both declared-entry attempts and whole-map retries, while this step defers verification of a separate one-key byte-capture path, instead of selecting single-key capture from numkeys alone. Scripts hold declared entries plus Meta until fallback requires the whole map; growing keys therefore still incur complete image copies. Reopen under firn-script-keys when capture evidence covers the one-key narrow path, abandonment and whole retry as separate attempts ([attempt publication](../../../research/investigations/script-engines/README.md#metadata-sequence-numbers-capture-expiry-and-eviction)).

Decision: A scan step or a capture copies a key's complete image in one hold however large, limited only by the reserve R (the scan step holds the key's image and its copy in the step buffer, and a capture its scratch image and journal copy, so the largest key a rewrite carries is about R/2, 8 MiB when maxmemory is zero; a larger key aborts every rewrite and, by the retry decision, stops automatic rewrites), because a per-key ceiling made every rewrite abort while any key above it existed, where main's replay and Redis rewrite such keys, instead of splitting a key across scan steps, which needs resumable iteration over Whitefoot's HashMap (status board item coord-wfbl-02-01). Splitting is safe in meaning: a key written between steps journals a complete image at its first write in the window, which replaces whatever the steps produced, so the earlier objection that split observations can produce a value that never existed no longer holds. The cost is a pause proportional to the key's size while it is copied, as Redis's own O(N) commands pause.

Decision: Each live scan step calls map_scan_within with the reserve left after the step's 64-KiB output buffer as its limit and charges the growth key_set_bytes reports across the call whatever it returns, because the owner's firn-q-rw-pace A ruling keeps R covering scan memory and map_scan_within bounds the call's whole heap growth by its limit, instead of map_scan with count hint 1 charged after it returns, which let one step exceed R by its keys. Key copies, images and buffer growth are charged before allocation without aborting. A one-position step that does not fit, whether map_scan_within refuses its first position or a copy does not fit, is discarded unwritten with its cursor kept, waits outside every hold and retries while its need so far could fit R less admission's fixed charge (for a refused position, also less a fresh KeySet's bytes and the step buffer), because journal staging and statement scratch drain and free the rest, and otherwise aborts with reserve, since no drain can make room. The fresh KeySet is made with capacity 0 and its key_set_bytes charged at creation, because key_set_new states no byte bound to charge before it allocates ([bounded scan](../../../research/investigations/aof-rewrite/scan-pace.md#design)).

Decision: The scan runs steps back to back and sleeps outside every hold once about 1 ms has passed since it last waited, with a count hint of about that many keys per step, whole positions kept together, starting at 64 that halves after a step writing more than 64 KiB and doubles after one writing at most 32 KiB, because the owner's firn-q-rw-pace A ruling yields the driver once per time slice so that a million keys scan in seconds, instead of a 100-microsecond sleep after each one-key step, which the driver's millisecond timer stretches to about a millisecond per key. A step of several positions whose copies do not fit is discarded unwritten and retried at hint 1 at once, so a larger hint never aborts a rewrite that one position per step completes ([pacing](../../../research/investigations/aof-rewrite/scan-pace.md#design)).

Decision: CONFIG answers rdb-key-save-delay as Redis 7.0.15's hidden integer parameter, and a nonzero value makes the scan take one position per step and a positive one sleep its microseconds per key, read at each step, because cases that act during a rewrite need it to stay in progress and Redis's own suite uses this parameter for that, instead of a firn-only test hook or fixtures large enough to outlast a time-sliced scan, which race it. Redis's forked rewrite keeps the value it started with and sleeps at random for a negative value; firn sleeps one microsecond per |value| keys, every sleep rounded up to whole milliseconds by the driver's timer, and takes a delay in slices of at most 100 ms that end when CONFIG SET changes the value or the rewrite is cancelled, so SHUTDOWN stops a delayed rewrite within about 100 ms where Redis kills its rewrite child ([testing delay](../../../research/investigations/aof-rewrite/scan-pace.md#testing-delay)).

Decision: BGREWRITEAOF answers started after S0 admission, because the rewrite is asynchronous and firn-q-rw-limits A selects later failure reporting through INFO, instead of delaying the reply until rotation. A rewrite remains in progress until its worker and retained journal chunks have been released; a new attempt cannot reuse their reserve early. Ordinary service pressure uses eviction or OOM rather than aborting a rewrite. Over-limit eviction does not wait for an aborted attempt's cleanup, which releases the ledger that is already excluded and gives eviction no extra room. After installation commits under Meta, eviction waits for publication and cleanup, because the manifest publication must finish with one authoritative outcome just as it must under shutdown.

Decision: The firn-only INFO fields firn_aof_rewrite_reserve and firn_aof_rewrite_scan_peak expose the admitted allowance and the largest observed PRE-2 heap increase across KeySet creation and one map_scan_within call, because the long-key regression needs allocation evidence independent of the reservation ledger under the reported-facts rule, instead of testing accounting against itself. The field firn_aof_rewrite_cut reports whether the latest admitted attempt actually crossed S1, because the backlog regression must distinguish post-cut buffer growth from scan-journal exhaustion. The scan-peak field is a process-wide before/after sample, not total rewrite peak or RSS; the regression uses one quiescent key and checks the necessary bound that even one step must fit R. Concurrent unrelated allocation or release can affect the sample, so it is not a general exact-reserve proof. `firn_aof_rewrite_charged` is reported in INFO Persistence with the other firn-only rewrite fields, beside `mem_aof_buffer` and `mem_not_counted_for_evict` in Memory: the exclusion is `mem_aof_buffer` plus the ledger less this rotation charge, so a check can show that rotation charges are subtracted once, which the total alone cannot show.

Decision: Collecting-buffer growth while the sole writer seals and rotates also consumes R, using a separate statement-local LogBudget committed with the mutation under Meta, because maxmemory excludes ordinary AOF capacity and constant-sized live values can otherwise grow an unbounded post-S1 backlog, instead of treating reuse of the two buffer owners as a capacity bound. The encoder charges full new backing capacity before growth, including overlap; an overflow marks capture failed before the ordinary append proceeds, and the writer checks cancellation before publication, including between chunks when exceptional boundary rereading is needed. Before publication it continues on the old file. Private command-effects buffers and non-command byte builders remain ordinary allocations; only their final collecting-buffer append uses this rotation budget.

Decision: Rewrite diagnostics report the first failure cause and its reserve use and peak, latched under Meta before cleanup, plus counts of complete image and effect records successfully appended to the journal file and completed scan steps with scan completion, because an undifferentiated error and post-cleanup ledger cannot distinguish the resource or I/O condition that stopped an attempt under the [reported-facts rule](../reported-facts.md), instead of replacing the initiating cause with a later cleanup error. File-record counts can lag committed writes while staging drains. Admission resets these facts; successful completion keeps an empty reason, zero current use and the attempt's peak and counters. These are reserve-ledger and progress facts, not independent heap measurements.

Decision: INFO reports each failed journal close or removal step in the latest attempt through firn_aof_rewrite_cleanup_failed, separately from the first abort cause, and preserves the latest unlisted-journal removal observation across admissions through firn_aof_rewrite_journal_leftover, because cleanup can fail after another cause or during startup before any attempt exists, instead of hiding cleanup errors behind the first failure or resetting startup evidence with attempt counters. The count includes early-error cleanup and resets on admission; startup does not increment it. The leftover flag is 1 after failed removal and 0 after observing absence or successful removal; it describes the last cleanup observation, not continuous filesystem monitoring.

Rejected:
- Counting rewrite memory within maxmemory, admitting only with R plus headroom below the limit: rejected because a cache at its limit can never rewrite, as reported in the 14900K cache sample [run 38395271960](https://github.com/Ming-Research/Firn-wf/actions/runs/38395271960), while Redis 7.2.16 does not count its rewrite child in maxmemory. The separate reserve retains a bounded rewrite allowance.
- Automatic retry after capture abort: rejected because reserve or value-size pressure can persist and repeated attempts would consume rewrite resources without owner action.
- A per-key work ceiling of 1024 payload visits or 64 KiB per scan step and per statement: rejected because any key above 512 elements or about 64 KiB then aborts every rewrite, a regression from main's replay and from Redis.
- map_scan with count hint 1, its KeySet charged after the call (the stage-2 limitation pending firn-gap-scan-bound): rejected because the call allocates a step's keys before any charge, so one long key exceeded R, and count is only a hint, so colliding keys could share the step.
- Charging the whole scan limit before the call and refunding what the KeySet did not retain: rejected because the reserve ledger's peak would then read nearly R at every step, hiding the attempt's real use, while holding Meta through the call already keeps every other charge out of that headroom.
- A 100-microsecond sleep after every one-key scan step: rejected because the driver waits for its earliest timer in whole milliseconds, so each step costs about a millisecond and a million-key scan cannot finish under write load.
- Eviction waiting for an aborted attempt's cleanup: rejected because the cleanup releases the ledger that the compared figure already excludes, so the wait gives eviction no room and only delays the victim statement.
