Decision: Replay applies the commands between `MULTI` and `EXEC` only once their `EXEC` is read, applies none of a block the file ends inside, passes over an `EXEC` outside a block, and advances only the clean-EOF truncation boundary to a nested `MULTI`, retaining the commands queued since the first `MULTI`, as Redis 7.2.16's loader does, because a write cut short leaves an unfinished block that must not apply in part, and scripts and transactions append their effects as blocks.

Decision: The last file whose end did not load is cut before anything is appended: after the last whole command when reading ends inside a command, even inside a block, and before the latest `MULTI` when the file ends cleanly inside a block, and never after a failed read; the server cuts it with `std::fs::truncate_file` before its writer starts and stops with status 4 when the cut fails, as Redis 7.0.15 cuts its file with `aof-load-truncated`, its default, because commands appended after a damaged end would otherwise follow bytes no replay can pass, instead of leaving the damaged end in place. As in Redis, a write appended to that last file after a cut inside an unfinished block is dropped by the next restart. An earlier base or incremental file whose end did not load stops firn with status 4 without cutting it.

Decision: A malformed AOF record stops firn with status 1 before it listens and logs Redis 7.2.16's bad-file-format message, leaving the file as it was; other unrecoverable startup refusals retain firn's status 4, because Redis 7.2.16 returns a loading failure on a format error and exits with status 1, and serving a keyspace that holds only part of the file loses later writes without notice, instead of accepting inline commands or starting with the commands read so far. At record boundaries only `*` begins a command and `#` skips one annotation chunk of at most 1023 bytes through its first LF, as Redis's 1024-byte `fgets` buffer does, instead of treating annotations as commands or skipping an arbitrarily long physical line.

Decision: Startup replay scans AOF headers with a bounded file buffer, keeps argument file positions, and rereads argument payloads into an exactly sized contiguous allocation for the existing command interface; transaction bodies are reread only after their `EXEC` is found, because the stored values and argument positions use 64-bit lengths and a command such as five 500-MiB list values is valid despite exceeding 2 GiB in total, instead of retaining a complete wire record or transaction in the network input window with its 2-GiB ceiling. The allocation and the loaded dataset must still fit available memory; startup adds no fixed total-record ceiling.

Decision: Active AOF error handling keeps firn's single appendfsync everysec policy, reopening selectable always and no policies and an appendfsync configuration only when a selected consumer needs them, because the current compatibility experiment needs recoverable write refusal within the existing durability contract, instead of adding unused durability modes and the reply barriers always would require ([investigation](../../research/investigations/aof-write-errors/README.md#proposed-design-and-alternatives)).

Decision: The sole AOF writer publishes separate saved append and sync IoErrors in Meta alongside its byte accounting, and network WRITE commands and PING observe failure at admission while mutations recheck under their existing Meta hold, because Meta already orders every mutation with writer publication and a preflight snapshot alone could admit a mutation after publication, instead of another Shared status object or continuing to acknowledge writes during a known persistence failure; reads and internal expiry or eviction remain allowed, as Redis 7.0.15 server.c:3881-3905,4324-4353 requires.

Decision: An incomplete append attempts truncation to the pre-flush incremental size, retaining the whole buffer on successful rollback or accounting the accepted prefix and retaining its suffix on failed rollback, and only a complete append clears its saved error, because Redis 7.0.15 aof.c:1146-1230 preserves exactly the bytes that still need writing, instead of always leaving a partial record in the file; the actual terminal IoError and whether the result was partial remain available so later error formatting can preserve Redis's ENOSPC normalization for partial results without discarding the host error.

Decision: Failed appends are retried every 100 ms whether or not clients write, because Redis 7.0.15 retries a retained buffer from beforeSleep on every event-loop iteration (server.c:1660-1666), and its loop wakes at least hz, by default 10, times a second for serverCron, which adds a once-per-second retry (server.c:1384-1393), so 100 ms is Redis's idle cadence, instead of the once-per-second cron retry alone or a retry on every writer tick; client traffic does not bring a retry forward, so under traffic firn can recover up to 100 ms later than Redis, a deliberate approximation of its per-iteration retry; a tick on which the retry is not yet due attempts no append and is not a writer failure ([method and rejection criteria](../../research/investigations/aof-write-errors/README.md#method-and-rejection-criteria-before-implementation)).

Decision: Outside shutdown the writer syncs the active file at most once a second, and only when nothing is retained and the file's incremental size differs from its size at the last successful sync, or when a sync error is saved, because Redis 7.2.16 flushAppendOnlyFile reaches its everysec fsync only after a complete write or, with an empty buffer, when aof_last_incr_fsync_offset differs from aof_last_incr_size (aof.c:1071-1094,1236-1267), and an idle sync with nothing new answers writes differently from Redis after a device fault: it fails at the first flush after the fault and refuses the next write with MISCONF, which Redis 7.2.16 acknowledges and refuses only once its sync after that write fails (aof-sync-fault job, CI run 38328422734 and earlier), instead of syncing once a second whether or not anything was appended; the once-a-second retry while a sync error is saved is the deliberate difference the next decision gives. The synced size is the active incremental file's size at its last sync that succeeded or failed with EINVAL; startup counts the loaded file as synced and rotation resets it with the incremental size, as Redis's aofOpenIfNeededOnServerStart and openNewIncrAofForAppend do (aof.c:762-763,842-845), and the timer advances only when a sync is attempted, as aof_last_fsync does.

Decision: After a failed sync of the active file the writer keeps syncing once a second even when nothing new was appended, and a later sync that succeeds, with no append error or retained byte left, does not clear the saved sync error but starts a recovery rewrite of the dataset from memory into a new base, incremental file and manifest; the error is cleared, and writes are admitted again, only in the Meta statement that ends a rewrite whose manifest was published and whose directory sync succeeded, and until then writes keep Redis's MISCONF refusal and INFO keeps aof_last_write_status:err, because Linux marks the pages whose writeback failed clean and reports the error to one fsync only, so the retried sync succeeds without writing them (in the aof-sync-fault job's page-end case, CI run 38324105320, a write acknowledged during the failure and a write acknowledged and synced after that retried sync were both missing after a remount and restart, while earlier data was intact), instead of clearing the error when the retried sync succeeds, or Redis 7.2.16's new-byte-dependent sync schedule in aof.c:1071-1094,1236-1267, which leaves an idle server refusing writes until a restart; recovery without a restart is a deliberate difference from Redis. Any rewrite whose installation is durable clears a saved sync error, manual and automatic ones included, because every sync error saved while a rewrite runs aborts it, so a durable installation holds a base written from memory after the error. Recovery attempts run whatever the automatic-rewrite block and are retried after each later successful sync, at most about once a second, unlike the automatic retry the owner's ruling A on firn-q-rw-limits excludes, because writes stay refused until one succeeds, so the retry is neither silent nor optional; a failed recovery attempt blocks automatic rewrites as any failed attempt does, and a successful one leaves the block as it found it. A sync failing with EINVAL counts as success, as Redis's bio.c:235-247 treats it: it latches nothing, so a file that cannot be synchronized does not refuse writes, and while a sync error is saved it starts recovery as a successful sync does. Append errors keep the complete-append rule above without a rewrite, because a failed write(2) neither marks pages clean nor consumes a writeback error, so the retained bytes written again reach the device with the rest.

Decision: A rewrite's new incremental file resets only its incremental-size accounting and preserves append and sync health except when a completed append clears its own error or a durable installation clears a saved sync error, because Redis 7.0.15 openNewIncrAofForAppend in aof.c:790-852 preserves those states and a successful sync of the sealed file after a failed one does not write the pages whose writeback failed, instead of applying startAppendOnly's CONFIG re-enable reset in aof.c:999-1013 to ordinary rotation.

Decision: All persistence refusals use one reply writer that emits Redis's exact MISCONF prefix followed by the host's description of the saved IoError, copied by std::io::error_copy_description into the reply window and sized from the length the host reports, selecting a failed append's own error when nothing of that append was written and otherwise the sync error, as Redis 7.0.15 writeCommandsDeniedByDiskError selects aof_last_write_errno (server.c:4324-4355, aof.c:1157-1162), because PRE-2's description of a host code is the host C library's C-locale message, the text Redis formats with strerror, instead of an errno-to-text table or an invented suffix that would conceal a language gap. A short write, which Redis reports as ENOSPC whatever the host returned (aof.c:1163-1184), is described by std::io::error_copy_class_description on a NoSpace carrying no host code, because that function returns the host's text for the class and firn's source then holds no platform number, instead of describing the short write's terminal error, hard-coding a host's ENOSPC number or substituting PRE-2's code-zero fixed text; a description the host reports unavailable leaves the suffix empty, because an empty suffix states no text the host did not give ([investigation](../../research/investigations/aof-write-errors/README.md#misconf-description-whitefoot-v0132)).

Rejected:
- Clearing a saved sync error when a retried sync succeeds (superseded): rejected because that sync does not write the pages whose writeback failed, so the server acknowledges new writes after a hole in its file and a restart loses the write acknowledged during the failure.
- Syncing once a second whether or not anything was appended (superseded): rejected because a device that fails while firn is idle then fails that idle sync first, and firn refuses with MISCONF a write that Redis 7.2.16 acknowledges (CI run 38328422734).
- Rewriting into the same file only the bytes appended since the last successful sync: rejected because it relies on that file's pages and size metadata after an error, which the page-end case showed are not written again: the write appended and synced after recovery was lost along with the one before it.
- Never recovering without a restart, as Redis 7.2.16 does: rejected because an idle server then refuses writes until an operator restarts it, and the restart still loses the write acknowledged during the failure; in the page-end case Redis 7.2.16 refused to load its file at restart and exited with status 1.
