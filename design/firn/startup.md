Decision: firn reads Redis 7.2.16's configuration syntax with an optional initial configuration filename or stdin -, followed by command-line directives introduced by every -- argument, applies those directives after file directives, and refuses unknown directives, because ordinary Redis deployments need their startup settings to be applied or explicitly refused, instead of firn's four positional arguments or ignoring unknown directives. This invocation does not consume a -- argument as a preceding directive's value or accept a trailing stdin -, and a first argument beginning with a single dash is a configuration filename ([invocation](../../firn/README.md#build-and-run)).

Decision: firn opens the configuration file, every `include` file, `dir`, `logfile` and the append-only files through Whitefoot's host-path interface, so that absolute paths work as in Redis 7.2.16, because the interface the interim relative-path rule waited for is delivered, instead of keeping the interim rule or refusing `include` and other `dir` values. Whitefoot has no change-directory call, so `dir` replaces the held pair of read and write directory handles with the opened directory, and every later relative path (a nested `include`, `logfile`, the append-only directory) resolves from it, the effect of Redis's `chdir`, instead of prefixing each path with the `dir` value or leaving the working directory unchanged. An `include` whose path holds `*`, `?` or `[` is refused with a diagnostic naming the glob, because Redis expands such a path with `glob(3)` and firn has no expansion, instead of opening the pattern as a literal file name ([path rules](../../firn/README.md#build-and-run)).

Decision: firn accepts port, bind, timeout, appendonly, appendfilename, requirepass, auto-aof-rewrite-percentage, auto-aof-rewrite-min-size, dir, logfile, loglevel, maxmemory, maxmemory-policy, maxmemory-samples, maxmemory-eviction-tenacity, lfu-log-factor, lfu-decay-time and maxclients as startup directives, plus the firn-only test directive below, because these settings control behavior firn implements and refusing other directives exposes compatibility still to be implemented, instead of silently accepting unsupported Redis directives even at their default values. Startup validates the six memory settings and maxclients, port and timeout through CONFIG SET's own validation code because both entry points must accept the same values and report the same reasons, instead of maintaining a second parser ([supported directives](../../firn/README.md#build-and-run)).

Decision: firn accepts one dotted IPv4 bind address or * and refuses multiple addresses and space-split address forms, because its server currently listens on one IPv4 socket and accepting Redis's several-address form would promise listeners it does not open, instead of ignoring extra addresses or expanding this startup change to multiple listeners. This is a firn limitation, not a Whitefoot limitation: the pinned std::net interface provides IPv6 socket addresses and independent tcp_listen calls. An empty bind, with zero values or one empty value, disables the listener as in Redis; without another listener firn exits 1 with the ordinary no-listener diagnostic ([binding](../../firn/README.md#build-and-run)).

Decision: firn uses the firn-only firn-clients directive to accept N clients then stop, with zero meaning no limit, because tests need a bounded server lifetime and a distinctive directive keeps this facility separate from Redis deployment settings, instead of retaining the positional client count ([test invocation](../../firn/README.md#build-and-run)).

Decision: firn refuses a naked argument after the configuration filename and before any -- directive, even when Redis would quote those arguments into a valid directive such as timeout 3, because an explicit -- boundary makes a misplaced extra filename or legacy positional argument an error, instead of Redis's implicit command-line configuration-line construction. Values following a -- directive remain its values until the next -- argument ([argument boundaries](../../firn/README.md#build-and-run)).

Decision: firn follows Redis 7.2.16's maxclients behavior through startup directives and CONFIG GET/SET, with default 10000 and range 1 through 4294967295, because compatibility requires the reference's client limit, refusal reply and connection counters, instead of divergent or unbounded admission and invented statistics. When the connected-client count meets or exceeds the limit, firn refuses a new connection before serving a command, sends exactly -ERR max number of clients reached followed by CRLF as a best effort and closes it. A refusal increments rejected_connections without changing connected_clients or total_connections_received; lowering the live limit leaves existing clients connected, and CONFIG RESETSTAT resets admitted and rejected totals ([setting](https://github.com/redis/redis/blob/7.2.16/src/config.c#L3209), [validation](https://github.com/redis/redis/blob/7.2.16/src/config.c#L2093-L2182), [live application](https://github.com/redis/redis/blob/7.2.16/src/config.c#L2556-L2576), [admission and counters](https://github.com/redis/redis/blob/7.2.16/src/networking.c#L1313-L1358), [statistics reset](https://github.com/redis/redis/blob/7.2.16/src/server.c#L2495-L2520), [operator behavior](../../firn/README.md#build-and-run)).

Decision: admission reads the current maxclients and updates the connected-client count in one atomic statement, and a refusal sends Redis's reply as a best effort under one shared one-second send deadline before closing, because a live CONFIG SET must not race admission and a refused peer must not hold firn's single accept loop without bound, instead of a separate read of the limit or waiting for a stalled refused peer. The deadline bounds waiting for a send that makes progress; the host send contract permits zero progress, so it is not a strict return-time bound ([operator behavior](../../firn/README.md#build-and-run)).

Decision: firn writes Redis 7.2.16's log line format, `pid:role dd Mon yyyy hh:mm:ss.mmm mark message` with the mark `.`, `-`, `*` or `#` for debug, verbose, notice and warning and the message cut at 1023 bytes, to standard output or to the file `logfile` names, at the `loglevel` threshold (default notice), because operators read Redis's log lines and the process id and local time are now available, instead of a firn-specific format or a partial one without them. The role is `C` for the first startup lines and `M` after, as in Redis; the time is the wall clock plus the host's local offset. Every context formats its line and puts it in one shared queue that one log context drains and writes, so lines are whole and in enqueue order and a slow terminal or file never stalls a command, instead of each context writing itself or holding a lock across the write; the queue is unbounded, so a line is never dropped, instead of a bounded queue that drops or blocks. A failed log write is dropped silently, as in Redis. The events logged are startup and the listening address, append-only file load start and end with the keys read, rewrite start and end, write failure and recovery, the stop signal and the stop; the wording follows Redis where Redis has the event and is firn's own otherwise ([log format](https://github.com/redis/redis/blob/7.2.16/src/server.c), [operator behavior](../../firn/README.md#build-and-run)).

Decision: firn follows Redis 7.2.16's adjustment of the open-file limit: at startup it raises the soft limit to maxclients plus 32 descriptors, trying 16 fewer after each refusal and, since Whitefoot reports the hard limit, going in one step to the value Redis's retry loop would reach; if the limit stays below what maxclients needs it lowers maxclients to what the limit supports and logs Redis's three warning lines, and at 32 descriptors or fewer it logs Redis's message and exits 1; `CONFIG SET maxclients` applies the same adjustment first and, when the operating system supports fewer clients than requested, replies with Redis's error naming the supported number and keeps the old value, because the Whitefoot capability firn waited for is delivered and an operator replacing redis-server expects `maxclients` to be a limit the process can honor, instead of leaving `ulimit -n` to the operator or only warning ([open-file adjustment](https://github.com/redis/redis/blob/7.2.16/src/server.c#L2278-L2354), [live apply](https://github.com/redis/redis/blob/7.2.16/src/config.c#L2556-L2576)). Two differences stay, both consequences of Whitefoot raising only the soft limit: Redis also sets the hard limit to the value it reached, so `/proc/<pid>/limits` shows the same soft limit but a different hard limit, and a process allowed to raise its hard limit (root) is not raised past it by firn; when the hard limit is below the request, the host's refusal Redis reports is `Operation not permitted` and firn's is `Invalid argument`, the same line otherwise ([operator difference](../../firn/README.md#build-and-run)).
